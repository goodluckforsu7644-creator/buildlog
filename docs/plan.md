# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. 서버에서도 사용 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- React 화면과 FastAPI JSON API를 분리합니다. 서버에서도 입력값과 권한을 검사합니다.
- 실제 DB는 Supabase PostgreSQL이며, 초기 개발·자동 테스트는 SQLite3로 진행합니다.
- Phase 0 결정: SQLAlchemy·Alembic·Vite와 FastAPI 자체 인증을 사용합니다. DB 세션·HttpOnly 쿠키·CSRF 검사를 적용하며 상세 기준은 `docs/setup.md`를 따릅니다.
- SQLite3 테스트와 별도로 Supabase PostgreSQL 검증을 완료해야 MVP가 끝납니다.
- `docs/spec.md`가 제품 요구사항 기준입니다. `frontend/mvp.md`는 초기 정리 자료로 참고하며 차이를 임의로 합치지 않습니다.
- 기존 `docs/README.md`는 유지하고 실행 안내는 `docs/setup.md`에 작성합니다.

## 3. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ requirements.txt
│  ├─ app/
│  │  ├─ main.py        # FastAPI 진입점
│  │  ├─ core/          # 환경 설정, 인증, 공통 권한
│  │  ├─ db/            # DB 연결과 세션
│  │  ├─ accounts/      # 회원 모델, 입력·응답 스키마, API, 서비스
│  │  ├─ records/       # 공부 기록, 할 일, 오류 기록
│  │  └─ community/     # 댓글, 좋아요, 신고
│  ├─ migrations/       # Alembic 단일 스키마 변경 이력
│  └─ tests/            # 모델·API·권한 테스트
├─ frontend/
│  ├─ package.json
│  ├─ src/
│  │  ├─ api/           # FastAPI 요청 공통 처리
│  │  ├─ pages/         # 화면과 이동 경로
│  │  ├─ components/    # 공통 UI
│  │  └─ styles/        # CSS
│  └─ tests/            # 화면·사용자 흐름 테스트
├─ database/
│  └─ buildlog.sqlite3  # 초기 개발용 데이터, Git 제외
└─ docs/                # 요구사항과 개발·실행 문서
```

## 4. 전체 개발 순서

| Phase | 만드는 결과 | 다음 Phase로 넘어가기 위한 핵심 조건 |
| --- | --- | --- |
| 0 | 개발 기준과 환경 확인 | 문서와 개발 환경에 충돌이 없음 |
| 1 | FastAPI·React 뼈대와 API 연결 | 양쪽 서버 실행과 화면의 API 호출 성공 |
| 2 | 사용자 모델과 데이터베이스 시작점 | 첫 마이그레이션과 사용자 모델 테스트 통과 |
| 3 | 회원가입·로그인·닉네임 | 회원 기능과 접근 제한 테스트 통과 |
| 4 | 세 가지 기록의 데이터 구조 | 저장·재실행·제약 조건 테스트 통과 |
| 5 | 공부 기록 전체 흐름 | 공부 기록 기능만 단독으로 완성 |
| 6 | 할 일 전체 흐름 | 할 일 기능만 단독으로 완성 |
| 7 | 오류 기록 전체 흐름 | 오류 기록 기능만 단독으로 완성 |
| 8 | 공개 기록·공개 범위·공개 검색 | 비공개 유출 없이 공개 기능 동작 |
| 9 | 댓글 | 댓글 조건과 권한 테스트 통과 |
| 10 | 좋아요 | 중복 방지와 취소 테스트 통과 |
| 11 | 신고와 운영자 확인 | 신고 저장·중복 방지·운영자 권한 확인 |
| 12 | 반응형 화면과 공통 오류 처리 | 360px 이상 화면과 지정 브라우저 확인 |
| 13 | Supabase PostgreSQL 연결과 검증 | 실제 DB에서도 스키마·권한·핵심 기능 통과 |
| 14 | 전체 통합 확인과 실행 문서 | `spec.md`의 완료 조건 전체 통과 |

## 5. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `docs/spec.md`, `docs/plan.md`, `frontend/mvp.md`를 확인합니다. 상세 계획의 추가 규칙과 초기 MVP 문서의 차이를 정리하고 제품 기준은 `docs/spec.md`로 둡니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. Python, Node.js, npm 설치 여부와 버전을 읽기 전용 명령으로 확인하고 FastAPI·React·개발 도구의 호환 버전을 선정합니다.
4. SQLite3 사용 가능 여부를 확인하고, SQLAlchemy·Alembic 및 PostgreSQL 드라이버 사용 계획을 확정합니다.
5. React `http://localhost:5173`, FastAPI `http://localhost:8000`, SQLite3 `database/buildlog.sqlite3`를 기본 제안으로 정리하고 API 주소·CORS 허용 출처·DB 연결 설정을 설계합니다.
6. 인증 방식을 결정합니다(Phase 0 결과: FastAPI 자체 인증). 쿠키·토큰 전달, 로그아웃·만료, CSRF·CORS 처리, 운영자 판정과 SQLite3 테스트 전략을 함께 정합니다. Phase 0에서 DB 세션·쿠키·CSRF 기준을 선택했고 자세한 내용은 `docs/setup.md`에 기록했습니다.
7. Supabase를 DB로만 쓰는 경우 서버 직접 연결을 기본안으로 삼습니다. 브라우저의 Data API 접근은 허용하지 않도록 스키마 노출·DB 권한을 설계합니다. 직접 클라이언트 접근을 선택할 경우 RLS 정책과 우회 경로까지 따로 검증합니다.
8. 테스트·서버 실행 명령을 문서에 기록할 준비를 하고 닉네임·입력 길이 등 계획에만 있는 세부 조건을 확정합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 실행 환경을 설명할 `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위가 충돌하지 않는지 확인합니다.
- Python·Node.js·npm 버전과 Python SQLite3 사용 여부를 읽기 전용 명령으로 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 완료 조건

- 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

### Phase 1. FastAPI·React 프로젝트 뼈대 만들기

#### 목표

React 화면에서 FastAPI 상태 확인 API를 호출하는 빈 서비스를 실행합니다.

#### 작업

1. `backend/.venv`를 준비하고 FastAPI·ASGI 서버와 확정한 도구를 설치해 버전을 기록합니다.
2. `backend/app/main.py`에 애플리케이션과 `/api/health`를 만듭니다.
3. `frontend/`의 기존 문서를 보존하면서 React 프로젝트와 패키지 잠금 파일을 준비합니다.
4. React 기본 화면, 공통 CSS, API 요청 모듈을 만듭니다.
5. React API 주소와 FastAPI 허용 출처를 환경별로 설정하고 브라우저 호출을 연결합니다.
6. 서버 설정은 환경 변수에서 읽고 `.env.example`에는 비밀값 없는 항목 예시만 기록합니다. `VITE_` 설정에는 공개 가능한 API 주소만 둡니다.
7. Git 준비 작업에서 이미 생성한 루트 `.gitignore`를 확인합니다. SQLite3·journal·wal·shm, 비밀 설정, 의존성·생성 파일·로그 제외와 중첩 `.env.example` 허용을 검증합니다.
8. Phase 0에서 정한 실행·테스트 명령과 작업 디렉터리를 `docs/setup.md`에 기록합니다.
9. 아직 사용자 테이블과 실제 데이터베이스를 만들거나 마이그레이션을 적용하지 않습니다.

#### 예상 변경 파일

- `backend/requirements.txt`, `backend/app/main.py`, `backend/app/core/config.py`
- `backend/tests/test_health.py`
- `frontend/package.json`, 패키지 잠금 파일, `frontend/vite.config.js`
- `frontend/index.html`, `frontend/src/main.jsx`, `frontend/src/App.jsx`
- `frontend/src/api/client.js`, `frontend/src/styles/base.css`
- `backend/.env.example`, `frontend/.env.example`, `.gitignore`, `docs/setup.md`

#### 확인 방법과 완료 조건

- 양쪽 서버가 실행되고 브라우저에서 API 상태 확인 결과가 보입니다.
- health API 자동 테스트와 React 기본 화면 테스트·빌드가 통과합니다.
- API 서버 중단 시 React가 실패 안내를 표시합니다.
- 비밀값이 프런트엔드 설정·응답·빌드 결과에 들어가지 않습니다.
- 사용자·DB·회원 기능은 다음 Phase에서 진행합니다.

### Phase 2. 사용자 모델과 첫 데이터베이스 만들기

#### 목표

이메일로 로그인하는 사용자 구조를 가장 먼저 확정하고 첫 데이터베이스를 만듭니다.

#### 작업

1. `backend/app/accounts` 모듈과 DB 연결·세션을 준비합니다.
2. SQLAlchemy 사용자 모델을 만듭니다. 정규화 이메일, 표시 닉네임, 중복 비교용 키, 비밀번호 해시, 운영자 여부와 DB 세션 모델을 준비합니다.
3. 이메일은 필수이며 중복되지 않게 합니다.
4. 닉네임은 필수이며 중복되지 않게 합니다.
5. 닉네임은 2~20자이고 한글, 영문, 숫자, 밑줄만 허용합니다.
6. pwdlib와 Argon2로 비밀번호를 해시하고 원문은 저장하지 않습니다.
7. 로그인 식별값을 이메일로 설정합니다.
8. 사용자·세션 모델을 DB 메타데이터에 연결하고 Alembic 첫 마이그레이션을 만듭니다.
9. 빈 SQLite 데이터베이스에 마이그레이션을 적용합니다.
10. 사용자 모델 단위 테스트를 작성하고 운영자 여부 필드와 서버 측 권한 판정 기반을 준비합니다. 회원가입 요청으로 운영자 권한을 설정할 수 없게 합니다.

#### 예상 변경 파일

- `backend/app/accounts/models.py`
- `backend/app/accounts/service.py`
- `backend/app/accounts/schemas.py`
- `backend/tests/accounts/`
- `backend/app/core/config.py`
- `backend/migrations/versions/`
- `database/buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 서로 다른 이메일과 닉네임으로 사용자를 저장할 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 확인합니다.
- 닉네임 길이와 허용 문자 검사가 동작하는지 확인합니다.
- 비밀번호 원문이 데이터베이스에 저장되지 않는지 확인합니다.
- 서버를 종료하고 다시 시작해도 사용자 데이터가 남아 있는지 확인합니다.

#### 완료 조건

- 첫 마이그레이션과 사용자 모델 테스트가 모두 통과해야 합니다.
- 사용자 모델을 다시 바꾸기 위해 데이터베이스를 지워야 하는 문제가 없어야 합니다.

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

사용자가 계정을 만들고 로그인한 뒤 자신의 닉네임을 바꿀 수 있게 합니다.

#### 작업

1. 회원가입 API와 React 폼·화면을 만듭니다.
2. 이메일 형식, 중복 이메일, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
3. 회원가입 실패 시 이메일과 닉네임은 유지하고 비밀번호만 지웁니다.
4. 성공하면 로그인 화면으로 이동합니다.
5. 로그인 API와 React 폼·화면을 만들고 이메일로 로그인하게 합니다. Phase 0의 세션·토큰·로그아웃·만료 처리 방식을 적용합니다.
6. 로그인 실패 시 이메일은 유지하고 비밀번호만 지웁니다.
7. 로그인 성공 시 내 기록 홈 화면으로 이동합니다.
8. 로그인하지 않은 사용자가 기록 화면에 접근하지 못하게 합니다.
9. 계정 설정에서 닉네임을 변경하게 합니다.
10. 공개 기록과 댓글에서 사용자 객체의 현재 닉네임을 읽도록 준비합니다.

#### 예상 변경 파일

- `backend/app/accounts/schemas.py`
- `backend/app/accounts/router.py`
- `backend/app/accounts/service.py`
- `backend/tests/accounts/`
- `backend/app/main.py`
- `frontend/src/pages/accounts/Signup.jsx`
- `frontend/src/pages/accounts/Login.jsx`
- `frontend/src/pages/accounts/Settings.jsx`
- `frontend/src/pages/Home.jsx`

#### 확인 방법

- `spec.md`의 회원 조건과 Phase 0에서 확정한 닉네임·비밀번호 경계값을 자동 테스트합니다.
- 회원가입 성공 후 로그인 화면으로 이동하는지 확인합니다.
- 로그인 성공 후 내 기록 홈으로 이동하는지 확인합니다.
- 실패 시 유지하거나 지울 입력값이 정확한지 확인합니다.
- 로그인하지 않은 사용자가 기록 URL에 직접 접근해도 볼 수 없는지 확인합니다.
- 다른 사용자의 닉네임을 바꿀 수 없는지 확인합니다.

#### 완료 조건

- 회원 관련 자동 테스트와 직접 화면 확인이 모두 통과해야 합니다.
- 이메일 확인과 비밀번호 찾기 기능은 만들지 않습니다.

### Phase 4. 공부 기록·할 일·오류 기록의 데이터 구조

#### 목표

9. 마이그레이션을 만들고 적용합니다.

### Phase 8. 공개 범위·공개 기록·공개 검색

#### 목표

7. 공개 오류 기록은 오류 제목·내용·해결 방법으로 검색합니다.

### Phase 11. 신고와 운영자 확인

#### 목표

로그인 사용자가 공개 기록이나 댓글을 신고하고 운영자만 신고 내용을 확인하게 합니다.

#### 작업

1. 신고 모델을 만듭니다.
2. 신고 대상은 공개 공부 기록, 공개 할 일, 공개 오류 기록 또는 댓글 중 하나로 제한합니다.
3. 신고 이유는 1~500자로 검사하고 앞뒤 공백을 제거합니다.
4. 한 사용자가 같은 대상을 한 번만 신고하게 데이터베이스 제약을 둡니다.
5. 신고 성공과 실패 안내를 만듭니다.

### Phase 13. Supabase PostgreSQL 연결과 호환성 검증

#### 목표

SQLite3에서 구현한 기능을 실제 DB인 Supabase PostgreSQL에서도 검증합니다.

#### 작업

1. 개발·검증 전용 Supabase 프로젝트와 연결 방식을 준비합니다. 실제 사용자 데이터가 있는 DB를 테스트 대상으로 사용하지 않습니다.
2. 서버 전용 `DATABASE_URL`을 안전한 로컬 환경 변수로 설정합니다. 브라우저에는 DB 비밀번호나 서버 전용 키를 전달하지 않습니다.
3. 동일한 모델·Alembic 이력으로 빈 PostgreSQL에 스키마를 적용합니다. DB별 차이가 필요한 부분은 명시적 마이그레이션으로 관리합니다.
4. 외래키, 길이·상태 제약, 중복 이메일·닉네임·좋아요·신고를 실제 PostgreSQL에서 확인합니다.
5. 시간대, 기본값, NULL 처리, 정렬, 한글·대소문자 검색 결과를 두 DB에서 비교합니다. SQLite3 테스트에서는 외래키 검사를 켭니다.
6. 사용자 A·B와 운영자로 공개·비공개·댓글·좋아요·신고 API를 다시 검증합니다.
7. 앱 테이블의 Data API 노출과 DB 권한을 점검합니다. 서버 경유 정책이면 브라우저 우회 접근을 차단하고, 직접 접근을 채택했다면 RLS 정책도 검증합니다. RLS만으로 FastAPI 권한 검사를 대체하지 않습니다.
8. FastAPI 자체 가입·로그인·세션 만료·로그아웃이 PostgreSQL에서도 동작하는지 확인합니다. Supabase Auth는 사용하지 않습니다.
9. SQLite3 테스트 데이터는 자동 이관하지 않습니다. 이관 필요 여부를 별도로 정하고, 연결 문자열 변경이 데이터 복사를 의미하지 않음을 문서에 기록합니다.
10. 연결·검증 방법과 환경별 실행 명령을 `docs/setup.md`에 기록합니다. 원격 테스트 정리는 전용 테스트 데이터 범위로 제한합니다.

#### 예상 변경 파일

- `backend/app/core/config.py`, `backend/app/db/`, `backend/migrations/`
- `backend/requirements.txt`, `backend/tests/integration/`
- `.env.example`, `docs/setup.md`, `docs/acceptance.md`

#### 완료 조건

- Supabase에서도 마이그레이션과 핵심 데이터·권한 테스트가 통과합니다.
- 테스트가 실제 사용자 데이터에 영향을 주지 않습니다.
- SQLite3와 PostgreSQL 결과 차이가 해결되거나 허용 근거가 기록되어 있습니다.
- Supabase 준비가 안 되어 있으면 이 단계는 미완료이며 SQLite3 검증으로 대체하지 않습니다.
